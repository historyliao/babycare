# 设计方案：宝宝作息记录小程序

> 目标用户：一个家庭里的 2–5 位照护者（爸妈、老人、月嫂），在**一只手抱娃**的状态下记录与查看。
> 核心约束：**数据不能丢**。

---

## 1. 一页纸结论

| 问题 | 选择 | 理由 |
| --- | --- | --- |
| 后端 | **微信云开发**（云函数 + 云数据库 + 云存储） | 免服务器、免域名、免备案；小程序体验版即可长期自用 |
| 权威数据 | 云数据库 `records` 集合 | 多设备共享、平台侧多副本 |
| 写路径 | **本地优先**：先落 `wx.setStorageSync`，再异步上云 | 抱娃时网络抖动不能阻塞记录；离线也能用 |
| 删除 | **软删除**（`deleted: true`） | 误删可恢复，且多设备能同步"删除"这个动作 |
| 每日总时长 | **按自然日裁剪后累加**（跨天夜觉拆到两天） | 符合"这一天到底睡了多久"的直觉，见 §5 |
| 客户端 ID | `_id` 由客户端生成并直接作为云端 `_id` | 重试幂等，弱网不会产生重复记录 |
| 家庭共享 | 邀请码 6 位 + `users.activeFamilyId` | 数据按 `familyId` 隔离，服务端反查，客户端无法伪造 |
| 防丢 | 云数据库 + 本机缓存 + 每日云端快照(30 天) + CSV 导出 | 四层相互独立，见 §8 |

已实现并可运行：**小程序端 + 微信云开发**，70 条自动化测试（23 统计口径 + 14 同步引擎 + 6 传输层 + 27 云函数）。

> **落地方式（2026-11-04 决策）**：小程序只做**体验版**（不提交审核、不发布），后端使用**微信云开发**，不备案、不用服务器，¥0/月。
> 体验版本身没有过期时间；但云开发的免费活动截止 **2026-12-31**，之后的三条退路见 [PLAN.md](PLAN.md) §7。
> 执行清单与验收标准同见 [PLAN.md](PLAN.md)。

## 2. 范围

### 做（P0，已实现）

- 睡眠：一键开始 / 结束，起止时间、时长、每日总时长、夜间与白天的拆分。
- 喝奶：亲喂（左 / 右 / 换边）、瓶喂母乳、配方奶（带 ml）、时长或次数统计。
- 今日概览：今日总睡眠、夜间时长、小睡次数、今日喂奶次数与奶量。
- 24 小时时间轴：一眼看出今天睡了几段、什么时候喂的。
- 明细：按天分组，可筛选、补录、编辑、删除。
- 统计：近 7 / 30 天的每日睡眠柱状、日均值、每日喂奶次数与奶量。
- 家庭共享：邀请码加入，多人实时看到同一份数据。
- 离线可用、夜间模式、CSV 导出、云端快照。

### 不做（明确排除，避免范围蔓延）

- 不做社交、排行榜、内容社区。
- 不做医疗建议或生长曲线判断（涉及医疗资质与免责风险）。
- P0 不做多宝宝（数据模型已预留 `type` 维度，见 §12 路线图）。

## 4. 技术选型

### 4.1 三个候选

| 方案 | 部署成本 | 数据归属 | 家庭共享 | 结论 |
| --- | --- | --- | --- | --- |
| A. 微信云开发 | 无需服务器，工具内一键部署 | 自己的云开发环境 | 云函数内做，简单 | ✅ **采用** |
| B. 自建后端（Node + 数据库） | 需服务器、域名、ICP 备案、HTTPS 证书、运维 | 自己的服务器 | 需自己写登录鉴权 | 备案 + 运维成本高，不采用 |
| C. 纯本地 `wx.setStorage` | 零 | 只在那台手机上 | ❌ 不可能 | 仅作缓存层 |

选 A 的原因：小程序 `wx.request` 只能访问**已备案且配置在小程序后台的 HTTPS 域名**，而云开发走微信私有通道（`wx.cloud.callFunction`），不受这条约束；同时把「鉴权 + 存储 + 部署」一次性解决。

对家庭自用场景，这三点刚好吃掉全部痛点：不用买域名、不用等备案、不用维护服务器。代价是数据在腾讯云，且免费额度有政策窗口（见 §10）。

### 4.2 为什么不是「把数据只存在手机里」

手机丢失、换机、微信清理缓存都会导致本地数据消失，且家人之间无法共享。本地存储只作为**缓存与离线队列**，不作为权威数据。

### 4.3 如果将来要迁到自建后端

数据模型与接口是刻意做成可以平移的：

- 云函数里的 `action` 路由（§7）可以直接映射成 REST 路径。
- `_id` 已经是客户端生成的字符串，迁移时无需重新编号。
- 时间统一存 UTC 毫秒数，不依赖数据库时区。
- 迁移步骤：导出 `records`（控制台导出 JSON/CSV）→ 导入你选的数据库 → 写一个服务端（可直接对照 `cloudfunctions/api/index.js` 移植业务规则）→ 把 `miniprogram/utils/api.js` 里的 `callFunction` 换成 `wx.request` 封装，**页面代码一行不用动**。

## 5. 统计口径（最容易被误解的部分）

### 5.1 每日总睡眠 = 与该自然日重叠的时长之和

把每条睡眠记录裁剪到当天的 `[00:00, 24:00)` 窗口后累加：

```
当日睡眠分钟数 = Σ max(0, min(end, 当日24:00) - max(start, 当日00:00))
```

- 进行中的记录（`endAt = null`）按「现在」截断，且不越过 24:00。
- 因此 `22:00 → 次日 06:00` 记为 **当天 2 小时 + 次日 6 小时**，两天相加正好 8 小时（守恒）。

**为什么不按「入睡日归属」**：那样 8 小时会全记在入睡当天，于是"昨天睡了 9 小时、今天只睡了 5 小时"这种数字会误导——今天那 5 小时其实是昨晚延续过来的。按重叠计算，手机上「今日睡眠」就等于"从今天 0 点到现在，孩子实际闭眼了多久"，和直觉一致。

代价是：**今天的数字要到当天结束才完整**。所以统计页明确标注「今天只统计到当前时刻」，避免拿半天和整天比。

### 5.2 夜间 vs 小睡

夜间窗口固定为 **`[19:00, 次日 07:00)`**（可在 `miniprogram/config.js` 调整）：

```
夜间分钟 = 该段睡眠与 [00:00,07:00) 和 [19:00,24:00) 的交集之和
小睡分钟 = 当日总睡眠 - 夜间分钟   （不小于 0）
```

一段睡眠若跨过 19:00 边界（如 18:00–19:30），会被拆成 60 分钟小睡 + 30 分钟夜觉；若某段被夜间窗口覆盖过半，则整段在列表里标记为「夜觉」。

### 5.3 喂奶的归属

喂奶按**开始时间**归属到某一天，不跨天拆分（一次亲喂 20 分钟跨过 0 点的情况可以忽略，强拆反而奇怪）。奶量只统计瓶喂；亲喂统计次数与总时长。

### 5.4 边界规则汇总

| 情况 | 处理 |
| --- | --- |
| 记录恰好 24:00 开始 | 归下一天 |
| 记录跨月 / 跨年 | 正常拆分，`dayKey` 用 `Date.UTC` 计算，无夏令时问题 |
| 时区 | 全部按固定 `UTC+8`（`TZ_OFFSET_MIN = 480`），中国无夏令时，避免 IANA 数据漂移 |
| 单条记录上限 | 48 小时，超出判定为误操作并拒绝 |
| 未来时间 | 服务端拒绝「开始时间晚于现在 5 分钟」以上的记录 |
| 已删除记录 | 不参与任何统计 |

以上规则全部有单测覆盖（`tests/stats.test.js`）。

## 6. 数据模型

### 6.1 集合一览

```
users       openid → 当前家庭组（鉴权入口）
families    家庭组、成员 openid、邀请码、时区偏好
records     睡眠 / 喂奶记录（核心数据）
backups     快照元信息（指向云存储文件）
```

### 6.2 `records`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `_id` | string | **客户端生成**，`r_` 前缀，6–48 位 `[A-Za-z0-9_-]` |
| `familyId` | string | 服务端写入，绝不接受客户端传值 |
| `type` | `'sleep' \| 'feed'` | 记录类型 |
| `startAt` | number | UTC 毫秒 |
| `endAt` | number \| null | `null` 表示进行中 |
| `feedKind` | `'breast' \| 'bottle_breast' \| 'formula' \| null` | 喂养方式 |
| `side` | `'left' \| 'right' \| 'both' \| null` | 亲喂侧 |
| `amountMl` | number \| null | 1–1000，仅瓶喂 |
| `note` | string | ≤ 200 字 |
| `deleted` | boolean | 软删除标记 |
| `deletedAt` | number \| null | |
| `createdBy` / `updatedBy` | string | openid |
| `createdAt` / `updatedAt` | number | **服务端时间**，是同步游标的依据 |
| `schemaVersion` | number | 便于将来迁移 |

### 6.3 `families`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `_id` | string | |
| `name` | string | 家庭名，默认「我的家庭」 |
| `ownerOpenid` | string | 创建者 |
| `members` | string[] | 成员 openid，上限 10 |
| `inviteCode` | string | 6 位，去掉 `0/O/1/I` 等易混字符 |
| `tzOffsetMin` | number | 480 |
| `nightStartHour` / `nightEndHour` | number | 19 / 7 |
| `createdAt` / `updatedAt` / `schemaVersion` | | |

> 成员 openid 列表**不下发**给客户端（`publicFamily()` 只返回 `memberCount`），减少信息暴露。

### 6.4 `users`

| 字段 | 说明 |
| --- | --- |
| `openid` | 微信用户唯一标识（唯一索引） |
| `activeFamilyId` | 当前所在家庭组；换家庭组就是改这一个字段 |

> 用独立的 `users` 表而不是直接按 `families.members` 反查，是为了支持「加入新家庭组后仍能切回原来的」——`members` 保留历史关系，`activeFamilyId` 决定当前视图。

### 6.5 索引建议

| 集合 | 索引 | 用途 |
| --- | --- | --- |
| `records` | `familyId` + `updatedAt`（升序） | 增量同步主查询 |
| `records` | `familyId` + `startAt` | 导出、区间查询 |
| `records` | `familyId` + `type` + `endAt` | 查「进行中的睡眠」 |
| `families` | `inviteCode`（唯一） | 邀请码加入 |
| `users` | `openid`（唯一） | 鉴权入口 |

家庭数据量很小（见 §10），不建索引也能跑，但建了更稳。

## 7. 接口设计

所有客户端调用都走**一个云函数 `api`**，用 `action` 路由，返回统一结构：

```json
{ "ok": true,  "data": { } }
{ "ok": false, "error": { "code": "ACTIVE_EXISTS", "message": "…", "data": { } } }
```

| action | 入参 | 出参 | 说明 |
| --- | --- | --- | --- |
| `family.bootstrap` | — | `{family, isNew}` | 首次调用自动建家庭组；幂等 |
| `family.join` | `{code}` | `{family, joined, migrated}` | 加入家庭组；若原家庭组只有自己，**自动迁移记录** |
| `family.rename` | `{name}` | `{family}` | |
| `records.upsert` | `{record}` | 服务端文档 | 新增/覆盖；`_id` 幂等 |
| `records.list` | `{since, skip, limit}` | `{records, count, hasMore, serverTime}` | 增量拉取（含软删除记录），分页 |
| `records.get` | `{id}` | 文档 | |
| `records.remove` | `{id}` | `{_id, deleted, updatedAt}` | 软删除 |
| `records.export` | `{from, to}` | `{rows, csv, filename}` | 带 BOM 的 CSV，≤ 5000 行 |
| `system.init` | — | `{collections}` | 建集合（部署后自检用） |

另一个云函数 `backup`：

| 触发 | 入参 | 行为 |
| --- | --- | --- |
| 定时（每天 03:30） | — | 备份**所有**家庭组到云存储，清理 30 天前的快照 |
| 小程序内手动 | `{scope:'family'}` | 只备份当前家庭组，返回文件名 |

### 7.1 鉴权与隔离

```
客户端 → 云函数 api → getWXContext().OPENID
                    → users 表查 activeFamilyId
                    → families 表校验
                    → 所有读写强制 where({ familyId })
```

客户端传什么 `familyId` 都会被忽略；改别人的记录会在 `doc.get()` 后被 `FORBIDDEN` / `NOT_FOUND` 拦下（已有测试覆盖）。数据库集合权限设为**仅管理端可读写**，客户端无法绕过云函数直连。

### 7.2 并发约束：同一时刻只允许一段进行中的睡眠

两台设备同时点「开始睡觉」时，后到的那条会收到：

```json
{ "ok": false, "error": { "code": "ACTIVE_EXISTS",
  "data": { "activeId": "r_xxx", "activeStartAt": 1700000000000, "recordId": "r_yyy" } } }
```

客户端（`pages/home/index.js` 的 `flush()`）会自动把旧的一段在 `新记录.startAt` 处收口，然后重试一次，**不打扰用户**。只在旧记录开始时间反而更晚时，才提示失败。

## 8. 数据持久化与容灾（"不能丢"具体怎么保证）


### 8.1 四层留存

```
写入
 │
 ├─① 本机 Storage（即时）        ← 离线可用、秒开；断网也不丢
 │     └─ dirty 标记，联网后补传
 │
 ├─② 云数据库 records（权威）    ← 平台侧多副本，多设备共享
 │
 ├─③ 云存储每日快照（03:30）     ← 独立于数据库；保留 30 天
 │     backups/2026-11-03/family-xxx-1699...json
 │
 └─④ 用户导出 CSV               ← 离机留存，可导入 Excel
```

四层相互独立：数据库被误删还有快照；快照过期还有 CSV；手机丢了换机登录同一微信，数据从云端回来。

### 8.2 写路径的可靠性

1. 写操作**先落本机**（`wx.setStorageSync`），UI 立刻更新——网络问题不影响记录。
2. 记录被标记 `dirty`，`sync()` 串行推送；失败的留在队列里。
3. 每次 `onShow` / 下拉刷新 / 任意写操作后都会尝试同步，所以断网恢复后无需用户干预。
4. **幂等**：`_id` 由客户端生成，`doc(id).set()` 覆盖写。超时重试 100 次也只会有 1 条。

### 8.3 增量同步协议

```
上行：dirty 记录逐条 records.upsert
下行：records.list({ since: lastSyncAt - 120000, skip })
      → 按 updatedAt 升序返回（含 deleted:true），单页 800 条
      → hasMore 为真则按 skip 翻页，最多 20 页，避免单次响应过大
      → 拉完：lastSyncAt = serverTime（查询开始时刻，避免漏数据）
      → 没拉完：lastSyncAt = 最后一条的 updatedAt（下次从断点继续）
```

- 服务端 `updatedAt` 一律用云函数时间，客户端时钟不准也不影响游标。
- 回看 2 分钟缓冲，防边界丢数据。
- 本地比服务端新的记录（`dirty`）不会被下行覆盖。

### 8.4 删除与恢复

- 删除是软删除，记录仍在库里，只是不参与统计。
- **单条误删**：控制台把该文档 `deleted` 改回 `false`，并把 `updatedAt` 改成当前时间（让各设备能拉到这次"复活"）。
- **批量误删 / 误操作**：用快照恢复，步骤见 [DEPLOY.md](DEPLOY.md) 的「恢复演练」。
- **平台能力**：云开发控制台对数据库提供回档能力（按套餐，具体以控制台为准）。

### 8.5 明确的风险边界

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 手机丢失 | 无影响（数据在云端） | 换机登录同一微信即可 |
| 微信清理小程序缓存 | 本地缓存丢失，云端不受影响 | 下次打开自动全量重拉 |
| 云开发环境被删 | 数据全丢 | 快照在**同一环境的云存储**里，也会一起没；因此必须定期导出 CSV |
| 云开发欠费停服 | 无法读写 | 套餐自动续费；重要数据导出留存 |
| 快照在 03:30 之前崩溃 | 最多丢当天数据 | 重要节点手动点「立即生成云端快照」 |

> 诚实结论：**任何单云厂商方案都不是绝对的"不丢"**。本方案的作用是把「全丢」的概率压到很低，并给用户一条自助的、不依赖平台的退路（CSV）。如果要求更高，应增加「定期把快照同步到另一个云/对象存储」。

```
│ 00  06  12  18  24           │
├──────────────────────────────┤
│ 最近记录              补录 ›  │
└──────────────────────────────┘
```

关键交互决策：

- **按钮是状态机**，不是表单：进行中显示「已睡 42分 / 醒了」，否则显示「开始睡觉」。
- **换边 = 结束当前侧 + 新开另一侧**，这样每一侧的时长都准确，而不是只改一个字段。
- **瓶喂**用 `wx.showActionSheet` 选类型 + `wx.showModal({editable:true})` 输奶量，避免自定义键盘弹层的适配成本。
- 每次写操作都有 `wx.vibrateShort` 轻震，抱娃时不用看屏幕也知道记上了。

### 9.2 明细

按天倒序分组，每组头部显示「睡眠 12小时30分 · 喂奶 8 次」；顶部三段筛选（全部/睡眠/喂奶）；点任意条目进编辑页；右下角悬浮 `＋` 补录。

### 9.3 统计

近 7 / 30 天切换；四宫格日均值（睡眠、夜间、喂奶次数、奶量）；日柱状图用纯 CSS `width%` 实现（不引图表库，省体积也省兼容问题）；睡眠/喂奶两个维度切换。

### 9.4 设置

家庭组（邀请码复制 / 加入）、同步状态与待上传数量、导出 CSV、立即快照、夜间模式开关、清空本机缓存。

### 9.5 编辑 / 补录

日期与时间用系统 `picker`；`尚未结束` 开关用于补一条正在进行中的记录；瓶喂自动隐藏结束时间（视为瞬时事件）；删除有二次确认。

## 11. 安全与隐私

- 儿童作息属于个人敏感信息。数据只存在**用户自己的云开发环境**，不经过任何第三方分析 SDK（本项目没有埋点、没有广告）。
- 客户端不能直连数据库，所有访问过云函数并强制按 `familyId` 过滤。
- 邀请码 6 位（32 字符集 ≈ 10⁹ 组合）+ 成员上限 10 + 只能由已登录微信发起，爆破成本高；泄露后可重建家庭组。
- 不下发成员 openid 列表。
- 导出 CSV 由用户主动触发，文件只写到小程序沙箱目录再交给系统分享。

## 13. 已知限制

1. 多人**同时编辑同一条**记录时，以服务端到达顺序为准（后写覆盖），不弹冲突提示。家庭场景下概率极低；误改可从明细页再改回来。
2. 单条记录最长 48 小时；忘记点「醒了」跨了 3 天，会被拒绝，需要手动补录。
3. 快照是**每日**而非实时，最坏情况丢当天数据。
4. 强依赖微信生态，无法给非微信用户使用。
5. 统计时区固定为 UTC+8；出国期间看到的"今天"仍是北京时间。
6. 只做体验版：不能被搜索、不能分享给非成员、不支持支付；家庭记录用不到这些。
7. 云开发免费额度有政策窗口（2026-12-31），到期后要么付费，要么需要重写后端再迁走。
8. 数据在腾讯云，不在自己服务器上。
